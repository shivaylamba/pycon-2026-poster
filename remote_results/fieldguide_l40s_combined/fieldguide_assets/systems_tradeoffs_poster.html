Overview

Everyday LLM calls look simple from Python, but the real deployment decision is a tradeoff between quality, latency, VRAM, energy, and cost.

We benchmark code generation, summarization, chat, RAG-style search, and embeddings across model sizes, quantization levels, architectures, and CPU/GPU configurations.

Thesis: the most accurate LLM is often not the most economically efficient one. LLM deployment is a systems engineering problem, not just model selection.

Learning 1: Bigger Models Have Diminishing Returns
SAME ARCHITECTURE · DIFFERENT SIZES
Scaling parameters often increases infrastructure cost faster than model quality.

Same-family comparisons isolate parameter count: Gemma 2B/7B, Phi3 3.8B/14B, Granite 3B/8B/20B, CodeLlama 7B/13B where present.

Measured benchmark: toy/code score, energy, latency, and VRAMSAME-FAMILY SCALING
Score note: the quality panel is a tiny code-generation pass rate, not a claim that lower-parameter models are universally smarter. Developer lesson: bigger is not automatically cheaper, faster, more deployable, or more practical.
Learning 2: Quantization Changes the Economics of AI
SAME MODEL · DIFFERENT PRECISION
4-bit and 8-bit models often retain useful quality while reducing memory, energy, and latency.

Learning 3: No Single Model Wins Every Workload
SIMILAR SIZE · DIFFERENT ARCHITECTURES / WORKLOADS
The efficient model depends on whether you are doing code, summaries, chat, RAG, or embeddings.

“Best model” is the wrong question. Ask: best model for which workload, on which hardware, under what latency and energy budget?
CPU vs GPU: The Scale Inflection Point
HARDWARE SCALE · CONCEPTUAL HEURISTIC

Hardware choice changes when prompts, outputs, batching, or concurrency grow. Single-request latency is not the same as throughput.

Conceptual deployment heuristic, not measured concurrency dataCPU-ONLY VS GPU + BATCHING
CPU is reasonable for
  • prototyping
  • local scripts
  • tiny embedding jobs
  • single-user offline tools
  • low request volume
GPU becomes better for
  • long prompts / outputs
  • batch embeddings
  • multi-user chat
  • latency-sensitive services
  • high concurrency

Tiny embedding jobs may not amortize GPU overhead. Measure batch size before assuming the GPU path wins.

Practical Heuristics
#Heuristic
1Benchmark the workload, not the model card.
2If quality barely improves but joules rise, use the smaller model.
3If VRAM is the deployment constraint, use q4/q8.
4If the workload changes, re-benchmark; do not reuse one winner.
5If concurrency grows, use GPU batching.
6If the workload is tiny and local, CPU may be good enough.
7Track tokens/joule, not just accuracy.
